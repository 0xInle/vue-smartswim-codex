# AGENT.md

## Назначение

Этот файл служит рабочей памяткой для любой дальнейшей работы по проекту `vue-smartswim`.
Перед изменениями нужно сверяться с этим документом, чтобы:

- держать в голове текущую архитектуру;
- не ломать визуальный язык проекта;
- соблюдать существующие соглашения по Vue-компонентам и данным;
- принимать решения в стиле уже написанного кода, а не привносить случайные паттерны.

## Кратко о проекте

- Стек: `Vue 3`, `Vite`, `Vue Router`, `Pinia`.
- Основной формат компонентов: `Single File Component` с `script setup`.
- Проект сейчас построен как контентный сайт/лендинг школы плавания и соревнований `Smart Swim`.
- Основной акцент интерфейса: промо-страницы, визуальные секции, карточки, контентные блоки, расписания и описания соревнований.

## Архитектура проекта

### Базовая структура

- `src/main.js`:
  - создает приложение;
  - подключает `Pinia`;
  - подключает `router`.
- `src/App.vue`:
  - корневой layout;
  - всегда рендерит `AppFloatingHeader`;
  - выводит страницы через `RouterView`.
- `src/router/index.js`:
  - маршруты описаны централизованно;
  - используется `createWebHistory`;
  - есть `scrollBehavior` с возвратом в начало страницы.

### Папки и ответственность

- `src/pages`:
  - top-level страницы сайта;
  - каждая страница является самостоятельной entry-view.
- `src/pages/home/components`:
  - секции главной страницы;
  - крупные визуальные и контентные блоки.
- `src/pages/competitions/components`:
  - локальные составные части раздела соревнований.
- `src/pages/competitions/*.js`:
  - контентные данные для страниц соревнований;
  - проект уже использует вынос данных из шаблонов в JS-модули.
- `src/components`:
  - переиспользуемые глобальные компоненты;
  - сейчас ключевой пример: плавающий header.
- `src/theme.css`:
  - глобальные токены, шрифты, утилитарные классы и базовые reset-правила.
- `public/images`, `public/videos`, `public/fonts`:
  - статические ассеты проекта.

## Маршруты

Текущая карта маршрутов:

- `/` -> главная
- `/competitions` -> список соревнований
- `/competitions/archive` -> архив соревнований
- `/competitions/:slug` -> страница конкретной серии/турнира
- `/fees`
- `/documents`
- `/contacts`
- `/trainers`

При добавлении новых страниц:

- сначала проверять, подходит ли существующая структура `src/pages/...`;
- маршрут добавлять централизованно в `src/router/index.js`;
- если страница относится к разделу, держать ее рядом с разделом.

## Соглашения по Vue

### Компоненты

- Предпочтительный стиль: `template` + `script setup` + `style scoped`.
- Импорты обычно короткие и читаемые, с алиасом `@/`.
- Логика компонентов в основном простая и локальная:
  - `ref`, `computed`, `watch`, `onMounted`, `onBeforeUnmount`;
  - без лишней абстракции;
  - без преждевременного усложнения.
- Для общения между компонентами уже применяются нативные механизмы Vue:
  - `props`;
  - `emit`;
  - `defineExpose` для редких сценариев, как в scroll API секции.

### Данные

- Контентные массивы и описания лучше хранить в отдельных `.js` файлах рядом со страницей.
- Если контент объемный, не зашивать его напрямую в `.vue`, если его можно вынести в модуль данных.
- Для многострочного текста уже используется helper вида `block(...lines)`.
- При расширении структуры данных сохранять текущую форму объектов, если нет явной причины менять контракт.

### Router

- Навигация строится через `RouterLink`.
- Детальные страницы соревнований завязаны на `slug`.
- Для новых detail-страниц сначала проверить, можно ли вписаться в существующий slug-based подход.

## Стилистика и визуальный язык

### Общий характер UI

Проект визуально опирается на:

- спортивную промо-подачу;
- крупные заголовки;
- контрастные карточки;
- светлый фон;
- акцентные голубые и оранжевые оттенки;
- glassmorphism-эффекты, полупрозрачные слои, blur и мягкие тени;
- фото- и видео-блоки как часть атмосферы.

### Токены и цвета

Глобальные CSS-переменные находятся в `src/theme.css`:

- `--black`
- `--white`
- `--orange`
- `--aqua`
- `--cyan`
- `--light-blue`
- `--very-light-blue`
- `--box-shadow`
- `--error-shadow`

При новых стилях:

- сначала использовать существующие переменные;
- не вводить новые цвета без необходимости;
- поддерживать общую прохладную aqua/cyan/light-blue палитру с редкими теплыми акцентами.

### Шрифты

- Основной текст: `Nunito`.
- Акцентные заголовки: `Oswald`.

Наблюдаемый паттерн:

- обычный текст и интерфейсные подписи идут на `Nunito`;
- крупные hero/title элементы часто используют `Oswald`;
- часть новых экранов может осознанно смягчать стиль и временно обходиться без `Oswald`, но это решение должно быть намеренным.

### Классы и нейминг

- Используется BEM-подобный нейминг:
  - `block`
  - `block__element`
  - `block__element--modifier`
- Обычно один `.vue` = один визуальный block с собственным namespace классов.
- Не смешивать стили разных секций в одном нейминге.

### Layout-паттерны

Часто встречаются:

- `.container` как внешний ограничитель ширины;
- `display: grid` для двухколоночных hero и карточных секций;
- `display: flex` для вертикальных и горизонтальных групп;
- адаптация через локальные `@media`;
- большие секции с выразительными отступами и фоновой графикой.

### Визуальные правила

- Делать интерфейс выразительным, но не перегруженным.
- Сохранять ощущение спортивного бренда, а не административной панели.
- Избегать серого безликого UI.
- Новые блоки должны выглядеть родственными текущим секциям home/competitions.
- Если добавляется новый фон, градиент или карточка, он должен сочетаться с уже существующим стеклянным и светлым стилем.

## Практические правила по коду

### Когда меняется страница

- Сначала изучить соседние страницы этого раздела.
- Повторно использовать существующие компоненты или паттерны, если они уже подходят.
- Не дублировать один и тот же layout, если можно вынести его в компонент.

### Когда меняются стили

- Сначала проверить `src/theme.css` и уже существующие классы блока.
- Не выносить локальные стили в глобальные без причины.
- Предпочитать `scoped`-стили для секционных компонентов.
- Следить, чтобы mobile layout не ломался: проект уже использует адаптивные grid/flex-переключения.

### Когда добавляются данные

- Хранить их рядом с соответствующим разделом.
- Названия полей делать семантическими и в стиле уже существующих структур:
  - `title`
  - `subtitle`
  - `description`
  - `image`
  - `imageAlt`
  - `cards`
  - `faqSections`
  - `slug`

### Когда добавляется интерактивность

- Предпочитать простую декларативную логику на Vue.
- Не вводить сторонние библиотеки, если задача решается встроенными средствами.
- Если используется DOM API, делать это аккуратно и в духе текущего кода:
  - `requestAnimationFrame`;
  - `ResizeObserver`;
  - `scrollIntoView`;
  - корректная очистка listeners/observers.

## Что уже характерно для проекта

- Контент на русском языке.
- Alt-тексты для изображений заполняются.
- Визуальные блоки часто состоят из:
  - eyebrow/label;
  - крупного заголовка;
  - описания;
  - мета-карточек;
  - CTA или навигационного действия.
- Карточки и панели часто имеют:
  - `border-radius` 10-20px;
  - мягкие тени;
  - прозрачный фон;
  - `backdrop-filter`;
  - `color-mix` и `rgb(from ...)`.

## Чего лучше избегать

- Не вводить новый архитектурный стиль без необходимости.
- Не переносить в проект паттерны из SPA-админок, если они не соответствуют текущему сайту.
- Не делать классы слишком общими внутри `scoped`-стилей.
- Не смешивать структуру данных и представление хаотично, если данные можно держать отдельно.
- Не ломать текущий контентный тон проекта слишком "техническими" текстами.
- Не заменять существующие шрифтовые и цветовые решения на нейтральные дефолты.

## Быстрый чеклист перед любой задачей

Перед началом работы по проекту:

1. Открыть `agent.md`.
2. Проверить, к какому разделу относится задача: `home`, `competitions`, глобальные компоненты или routing.
3. Посмотреть соседние файлы этого раздела.
4. Свериться с существующим визуальным паттерном блока.
5. Только потом писать код.

Перед завершением изменений:

1. Проверить, не выбиваются ли классы и стили из текущего языка проекта.
2. Проверить, не стоило ли вынести контент в data-файл.
3. Проверить адаптивность и читаемость.
4. Проверить, не нарушены ли существующие маршруты и `slug`-связи.

## Рабочая установка для дальнейших задач

Если задача не требует иного, при работе по этому репозиторию нужно:

- сначала читать `agent.md`;
- ориентироваться на архитектуру и паттерны, описанные здесь;
- сохранять текущий визуальный язык Smart Swim;
- принимать решения в пользу локальной консистентности проекта.
